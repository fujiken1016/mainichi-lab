Cloudflare Pagesで内部ファイルを404にする方法、6通り試して効いたのは1つ（実測）

2026年11月10日 ／ フジケン

僕は個人で9つのWebサイトを運営しています（9サイトの検索流入の内訳は別の記事に書きました）。2026年8月、そのうちの1つで、リポジトリに置いていた運用メモがURLを打つだけで読めることに気づきました。README.md や、どの記事にどの広告を差し込むかを書いたメモです。

9サイトすべてを点検すると、同じ状態のファイルは2026年8月30日の時点で5サイト・20ファイルありました。8サイトはCloudflare Pagesで配信しています。そこで、ファイルを消さずに「URLでは読めない」状態にする方法を、本番で6通り試しました。

先に結論です。404にできたのは Pages Functions のミドルウェア（functions/_middleware.js）だけでした。_redirects に404を書く方法、ドット付きフォルダに移す方法、無視リストに書く方法は、どれも200のままでした。_headers の noindex は検索結果に出さない設定で、URLを知っている人は読めます。

1. 解説記事を3本開いて、足りなかったもの

書く前に、関連する記事を3本、本文まで開きました（2026年11月7日）。

1本目は、公開された .git ディレクトリから中身を復元する手順を解説した記事です。冒頭で「/.git/HEAD に1回リクエストすれば分かる」と答えを出し、検査コードとサーバーごとの塞ぎ方を並べていました。2本目は、約496万のIPで .git が読めたという2026年の調査を伝える記事です。3本目は、Cloudflare Pagesで410を返そうとして _redirects でつまずいた記事で、ステータスコードごとに使う仕組みを表にまとめていました。

この3本から、冒頭で答えを出すこと、検査を curl 1行で示すこと、方法を表で並べることを型として借りました。足りなかったのは、Cloudflare Pagesで「既にあるファイル」を隠す方法を複数並べて比べた実測です。410の記事は存在しないURLの話で、手元にあるファイルを404にしたい場合とは条件が違います。

2. 9サイトを点検して見つかったもの

点検は2回に分けて行いました。1回目は2026年8月13日、2回目は8月30日です。どちらも、存在しないはずのパスに curl でリクエストを送り、返ってきたステータスコードと本文を見ました。

curl -s -o /dev/null -w '%{http_code}' "https://example.com/README.md"

1回目（8月13日）で見つかったのは2種類です。1つ目は、存在しないURLでもトップページを200で返す「ソフト404」で、9サイト中5サイトがこの状態でした。Cloudflare Pagesは、公開フォルダに 404.html が無いとトップページを返します。5サイトとも 404.html を置いて直りました。

2つ目は、Cloudflare Pagesではない1サイト（Renderで動かしているもの）で、README.md や server.js、.git/ の一部が読めたことです。.git/config と中身のオブジェクトは404で、履歴は復元できない状態でした。このサイトは、配信してよいファイル名だけを並べた許可リスト方式に変えて塞ぎました。

.env と .git/config は、8月13日も8月30日も9サイトすべてで404でした。パスワードやAPIキーが外から読めた形跡はありません。

問題は、1回目に「検索に出なければよい」と判断して、運用メモに _headers で X-Robots-Tag: noindex を付けるだけにしたことです。2回目（8月30日）に測り直すと、noindex を付けたファイルも含めて、次の数が200で読めました。

食事記録アプリの10件には、サーバー側の Python ファイルや requirements.txt も入っていました。中身を確かめると、APIキーは環境変数から読む書き方で、ファイルには入っていませんでした。ほかのサイトの README.md と広告枠のメモも、本文を取得して広告IDや個人情報を探し、0件でした。

この20件とは別に、資格試験の学習サイトでは、広告の提携IDと、競合を調べたSEOのメモや運用手順書がそのまま読めました。広告IDは公開ページのリンクにも入っているので、IDそのものは秘密ではありません。読まれて困るのは、どの記事にどの広告をどう入れるかという計画のほうでした。

4. なぜ _redirects では404にならないのか

試した当日は「実在するファイルが _redirects より優先されるからだ」と考えて、メモにもそう書きました。この記事を書くためにCloudflareの公式ドキュメント（Redirects）を読み直すと（2026年11月7日）、別の理由が書いてありました。

公式の説明では、リダイレクトはファイルがあってもなくても適用されます。そのうえで、対応しているステータスコードは301・302・303・307・308の5つです。404など「ほかのステータスコードで返す書き換え」は、対応表で非対応になっていました。つまり、①と②が効かなかったのは、404という書き方そのものが対応外だったから、と読むのが公式の説明に合います。

当日の解釈は間違いでした。結果（200のまま）は変わりませんが、理由を取り違えたまま「静的ファイルが勝つ」と覚えていると、301で別のURLに飛ばすような使い方まで効かないと思い込んでしまいます。3本目の手本の記事も、410が無視された理由を同じく「対応コードは5つだけ」と説明していました。

⑥が効く理由は、公式のMiddlewareの説明にあります。functions フォルダの直下に _middleware.js を置くと、静的ファイルを返す前にも実行されます。

5. 効いた方法：ミドルウェアと _routes.json

実際にポータルサイトに置いたものは、次の内容です。.md で終わるパスと、名前を並べたファイルだけに404を返し、それ以外は context.next() でいつも通り配信します。

const DENY = new Set(["/.gitignore"]);

export async function onRequest(context) {
  const path = new URL(context.request.url).pathname;
  if (path.toLowerCase().endsWith(".md") || DENY.has(path)) {
    return new Response("Not Found", {
      status: 404,
      headers: { "content-type": "text/plain; charset=utf-8", "x-robots-tag": "noindex" },
    });
  }
  return context.next();
}

.md を拡張子でまとめて止めたのは、どのサイトにもMarkdownをそのまま見せるページが1つも無かったからです。それ以外は名前を1つずつ書きました。拡張子でまとめると、robots.txt や sitemap.xml、ads.txt まで巻き込むおそれがあるためです。

資格試験の学習サイトでは、さらに _routes.json の include に止めたい6つのパスだけを書きました。こうすると、ふつうのページはFunctionsを通らず、これまで通り静的に配信されます。代わりに、新しい運用メモをリポジトリの直下に置いたら、include にも書き足す必要があります。

入れる前と後で、正規のページが壊れていないかも測りました。8月30日に、ポータル10本、食事記録アプリ9本、ゲーム系サイト3つで8本・8本・7本のURLを測り、すべて200のままでした。食事記録アプリはすでにFunctionsでAPIを動かしていたので、ヘルスチェック用のAPIが200を返し続けることも確かめました。

なお、functions フォルダを足すと、そのサイトのデプロイはWorkerを含むビルドに変わります（メンテナンス中に503を返したときの検索への影響は503の実測記事にまとめています）。ビルドに失敗しても、1つ前のデプロイが動き続けるので、サイトが止まることはありませんでした。ただ、デプロイのたびに正規ページの200を測る手間は増えます。

6. 「直った」の判定でつまずいたこと

8月31日、資格試験の学習サイトで、リポジトリから消したはずのファイルが200で返ってきました。レスポンスヘッダーの age は1092で、CDNに残った古いコピーが返っていました。URLの末尾に ?cb= と適当な値を付けて、キャッシュを通さずに測ると404でした。

キャッシュを意識せずに1回だけ測ると、塞げていないものを「塞げた」と判定することもあれば、その逆もあります。それ以来、完了の判定は「そのまま」と「?cb= 付き」の両方で404になること、にしています。

8. この記録の限界

  • 6通りを試したのは、2026年8月30日時点のCloudflare Pagesです。仕様が変われば結果も変わる可能性があります
  • .assetsignore がPagesで使えないことは公式の説明を全文確認できておらず、ここでは「試して効かなかった」という実測だけを書いています
  • ①と②が効かなかった理由は、試した当日ではなく後から公式ドキュメントを読んで当てはめたものです。ほかの要因が重なっていたかは、切り分けて試していません
  • 点検で測ったのは、こちらで思いついたパスだけです。リポジトリの中身を全部数えて照合したわけではないので、名前を知らないファイルが残っている可能性はあります

一番確実なのは、そもそも公開しないファイルを配信するフォルダに入れないことです。
